# Multi-message orders and location

Customer webhook messages now enter a durable per-phone Redis FIFO before processing. An atomic enqueue deduplicates provider retries. A token-guarded worker retains the head until the bot's session/reply transaction finishes; a five-second recovery worker retries retained work after failure/restart. Existing bot dedup protects a crash between commit and queue acknowledgement. Queue capacity is 100 and each drain handles at most 25 messages. Staff attention/generation checks remain authoritative; old generations cannot replay after an operator resumes a chat.

Replies are held until the currently queued messages are processed, retaining the latest prompt rather than sending obsolete requests for name/address/location. This is not a typing detector: messages received after a drain completes may receive separate replies. Product additions can no longer become recipient names, and progress in a draft does not trigger the repeated-question handoff guard. The semantic auditor no longer treats a product with no required options as incomplete.

Validation: 258 compiled tests passed, one existing SQL test skipped; typecheck, production build and source/compiled runtime parity passed. 147 conversation simulations / 1,317 turns passed. A concurrent seven-message test preserves three products, native location, written address, delivery phone and name, emits one pending-data question, and creates exactly one mocked order only after confirmation. Isolated real Redis validation covers concurrent FIFO, deduplication, final-reply flush and recovery. No real customer messages or production orders were created.

Live Haiku evaluation through the new inbox also passed all 12 sequential turns with 35 successful AI requests and the current public catalog: six chicken pieces, three different small sides, crispy burger with fries, Coca-Cola 600 ml, location and contact data. Final mocked total $388 includes a synthetic $60 delivery fee. No external messages/orders. This evaluation does not assert that the live provider can never fail or that every future ambiguous request is resolved automatically.
